# 术语表规则(Glossary Rules)

> **本文档定义 glossary-agent 的转换规则**:从各需求文件 §4.1 归并跨需求的角色定义,
> 维护 `requirements/shared/ROLES-shared.md`;同时维护 `glossary.md` 的命名与缩写规范。
>
> 注意:glossary 通常是**项目级**的,跨多个需求共享。本 agent 默认行为是**增量更新**,不是每次重建。

继承:`global-rules.md`、`traceability-rules.md`

---

| 项 | 值 |
|---|---|

| **不做** | 业务规则定义、字段命名(data-contract 的事)、状态枚举(同上)、单需求内的业务术语(该需求 §6 的事) |

- **修改既有条目**: 必须由人类操作,agent 不主动改写

## 4. 转换规则详述

### 4.1 业务术语提取规则（已废止）

> **本节于 2026-08-08 废止**,因 `glossary.md` 的业务术语章节已移除。
>
> **废止原因**:原规则以「出现 ≥ 3 次」为候选判据,用的是**频次**而非**分布**。
> 实测表明该判据会选中最不需要全局登记的词 —— 「免审批」在需求中出现 76 次,
> 但 100% 集中于 REQ-003H 一份文件;而真正会漂移的是跨十几份需求出现的词。
>
> **替代做法**:跨需求的术语一致性由 §4.3 禁用词识别承担,判据改为
> **跨文件数 ≥ 5 且存在竞争写法**。单需求内的术语不进 glossary,
> 由该需求 §6 核心实体自行定义。
>
> 以下原规则内容保留备查,不再执行：

**步骤**:

1. **名词频率统计**:
   - 扫描需求全文,统计专有名词出现次数
   - 出现 ≥ 3 次的核心名词 → 进入 candidate 列表
   - 出现 1-2 次但属于业务核心(实体名、操作名)→ 进入 candidate

2. **过滤规则**(以下不进 glossary):
   - 通用词汇:用户、系统、功能、需求、页面、按钮、接口、数据
   - 技术术语:API、SQL、HTTP、JSON 等(进 §4 缩写表,不进 §1)
   - 形容词、副词:重要、快速、稳定

3. **生成条目格式**:

   ```markdown
   | 术语(中文) | 术语(英文/代码) | 定义 | 同义词/易混淆 | 反例 |
   |-----------|----------------|------|--------------|------|
   | [中文] | <!-- TODO: 英文待定 --> | [从需求上下文提取的定义] | <!-- TODO --> | <!-- TODO --> |
   ```

4. **定义提取规则**:
   - 若需求中有"[术语]:[定义]"的显式定义 → 直接使用
   - 否则从首次出现的上下文截取一句话作为定义
   - 定义长度控制在 30-80 字

5. **英文/代码命名**:
   - **不自动翻译**(易出错)
   - 标注 `<!-- TODO: 英文翻译 -->`,等人工确认
   - 例外:已有标准译法的(如"用户" → "user")可填,但加 `<!-- DERIVED -->`

6. **同义词识别**:
   - 扫描需求全文,寻找指代相同概念的不同名词
   - 输出到"同义词/易混淆"列,**并提示需要 PM 确认主称呼**
   - **不擅自判定**哪个对哪个错

---

### 4.2 技术缩写提取规则

**保留模板预填项**: AC / US / TC / OQ / API / DTO / SSoT(这些是文档体系自身的术语)

**新增规则**:
- 扫描需求中出现的英文大写缩写(2-5 字母)
- 上下文能识别全称的 → 添加
- 上下文识别不出的 → 标 TODO

---

### 4.3 禁用词识别规则

**登记判据**（2026-08-08 修订，替代原 §4.1 的频次判据）:

一个词进入 §6 禁用词表，须**同时**满足:

1. **跨文件数 ≥ 5** —— 出现在 5 份及以上的需求文件中
2. **存在竞争写法** —— 同一概念在不同文件中有两种及以上表述

> 只看频次会选错对象。实测：「免审批」出现 76 次但全部集中在单份需求，
> 无需登记；而跨十几份需求出现的词才是漂移高发区。
> 单需求内的术语由该需求 §6 核心实体自行定义，不进 glossary。

**典型同义词漂移场景**:

| 模式 | 处理 |
|-----|------|
| 同一段落两个不同名词指代同一概念 | 提示需要选其一作为标准 |
| 中英混用 | 由 PM 选定主用法，另一种登记为禁用词 |
| 缩写与全称并存 | 由 PM 选定主用法 |
| 全角 / 半角括号混用 | 中文语境统一全角（见 `glossary.md` §3.1 排版规范） |

**禁用词条目示例(模板,无业务内容)**:

```markdown
| ❌ 不要用 | ✅ 应该用 | 原因 |
|---------|---------|------|
| [缩写] | [全称] | 缩写易引起误解 |
```

> ⚠️ **agent 不主动判定哪个是错的**,只提示"以下两个词疑似同义",由 PM 决策。

## 7. 增量更新校验(再次运行时)

```pseudo
function update_glossary(new_terms, existing_glossary):
  for term in new_terms:
    if term in existing_glossary:
      log("skipped: %s already defined" % term)
    else:
      append_to_glossary(term)
      log("added: %s" % term)

  for term in existing_glossary:
    similar = find_similar_in(new_terms, term)
    if similar:
      warn("potential synonym: %s vs %s" % (term, similar))
```

## 8. 禁止事项

1. ❌ 修改已有术语的定义(由人类决策)
2. ❌ 自动翻译中文为英文
3. ❌ 删除既有条目
4. ❌ 把数据契约里的字段名当业务术语放进 glossary
5. ❌ 把通用词(用户/系统)放进 §1
6. ❌ 自动判定同义词中"哪个对哪个错"

---

## 9. 与下游 agent 的协作

glossary 生成/更新后,下游所有 agent **必须**:

- 在生成时引用 glossary 的术语
- 发现自己想用的词不在 glossary 中 → 报告给 PM,**不自创**
- 不能用同义词替换 glossary 已定义的词
