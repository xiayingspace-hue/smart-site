# 角色定义规则(Roles Rules)

> **本文档定义 roles-agent 的转换规则**:从各需求文件 §4.1 归并跨需求的角色定义,
> 维护 `requirements/shared/ROLES-shared.md`。
>
> 本 agent 默认行为是**增量更新**,不是每次重建。
>
> 命名与书写规范(ID 格式、文件命名、字段/枚举命名、全角半角)已并入
> `global-rules.md` §4、§9,不由本 agent 维护。

继承:`global-rules.md`、`traceability-rules.md`

## 2. 输入契约

### 2.1 必读输入

| 来源 | 章节 | 用途 |
|-----|------|------|
| `requirements/**/*.md` | §4.1 角色定义表 | 提取全部角色名 |

> 二者可能不一致(如 §4.1 写「项目管理人员 / Drawing 团队 / 管理员」而 §5 写
> 「管理员/Drawing 团队」),**必须同时扫描**,不一致时登记为待确认。

### 2.2 增量更新模式

- **首次生成**: 扫描全部需求,归并后初始化 `ROLES-shared.md`
- **再次运行**: 加载既有文件,**只新增**角色与禁用词,**不修改**已确立的标准名
- **修改既有标准名**: 必须由人类决策,agent 不主动改写

## 4. 转换规则详述

### 4.1 角色归并规则

**核心判据:不看名字看权限。** 两个写法是否为同一角色,依据以下证据链判断,
**不得**仅凭字面相似度归并:

| 证据强度 | 依据 | 示例 |
|---------|------|------|
| 强 | 持有相同的权限码 | 003G 的「项目管理员」与 007D 的「业务人员」同属 `drawing:` 权限域 → 同一角色 |
| 强 | 权限矩阵同构位置 | 003A 与 003C 的矩阵均为 4 列且列序一致,首列分别是「设计人员」「Drawing 团队成员」→ 同一角色 |
| 中 | 职责描述实质相同 | 两处均写「负责图纸分配,决定哪些 SE 可见」 |
| 弱 | 名字相似 | 「项目管理员」与「项目管理人员」—— **仅此不足以归并**,须有上述任一佐证 |

**ROLE-XXX 编号不可作为归并依据。** 该编号是需求文件内的局部编号,同一编号在
不同需求中含义不同(实测 `ROLE-001` 在 16 份文件中代表 10 种角色)。

**作用域判定**:角色只出现在特定模块、且与主线角色无权限交集时,登记到 §1.2
非图纸线角色并注明作用域,**不并入** §1.1。

### 4.2 禁用词登记判据

一个写法登记为禁用词,须**同时**满足:

1. **跨文件数 ≥ 5** —— 出现在 5 份及以上的需求文件中
2. **存在竞争写法** —— 同一角色在不同文件中有两种及以上表述

> 判据是**分布**而非**频次**。只看频次会选错对象:实测「免审批」出现 76 次,
> 但 100% 集中于 REQ-003H 单份需求 —— 这类词无需全局登记,由该需求自行定义。
> 真正会漂移的是跨十几份需求出现的词。

**典型漂移场景**:

| 模式 | 处理 |
|-----|------|
| 同一权限矩阵中两列指代同一角色 | 提示合并,由 PM 决定保留哪个名字 |
| 中英混用(如 `Admin` 与「管理员」) | 由 PM 选定主用法,另一种登记为禁用词 |
| 裸词与限定词并存(如「管理员」与「图纸管理员」) | 取更具体者为标准名 |
| 一列合并了多个角色(如「管理员 / Drawing 团队」) | **不是同义词**,提示拆分为独立列 |
| 全角 / 半角括号混用 | 中文语境统一全角(见 `global-rules.md` §9.1) |

> ⚠️ **高危模式**:两个写法仅差一个修饰词但含义相反。
> 实测案例:「业务人员」= 有 `drawing:dc-config` 权限,「普通业务人员」= 无任何图纸权限。
> 发现此类配对时**必须**在禁用词表中显式标注 ⚠️ 高危,不可只做静默替换。

> ⚠️ **agent 不主动判定哪个写法是错的**,只提示"以下两个写法疑似同一角色",
> 附上权限码等证据,由 PM 决策标准名。

### 4.3 限定写法识别

权限矩阵列头中形如「角色名(状态)」的写法,是**同一角色的状态限定**,不是独立角色:

| 写法 | 实为 |
|-----|------|
| `DC（已配置）` / `DC 自身` | Document Controller |
| `内部审批人（本人）` / `（他人）` | 内部审批人 |
| `设计人员（本图纸上传人）` | 设计人员 |

这类写法登记到 §2.2 说明其归属,**不得**当作新角色写入 §1。

## 5. 校验清单

通用清单外,本 agent 自检:

- [ ] §1 每个角色都有标准名,且全项目唯一(无两行指同一角色)
- [ ] §1 中出现的每个角色,都能在至少一份需求的 §4.1 或 §5 中找到出处
- [ ] §2.1 每条禁用词的"应该用"列,都指向 §1 中存在的标准名
- [ ] 归并决策均有权限码或矩阵同构佐证,无仅凭字面相似度的归并
- [ ] 高危配对(含义相反的近似词)已显式标注 ⚠️
- [ ] 作用域受限的角色已放入 §1.2 并注明适用 REQ

## 6. 增量更新校验(再次运行时)

```pseudo
function update_roles(scanned_roles, existing):
  for role in scanned_roles:
    if role.name in existing.standard_names:
      log("skipped: %s already standard" % role.name)
    elif role.name in existing.deprecated_terms:
      log("skipped: %s already deprecated → %s" % (role.name, mapping))
    else:
      candidate = find_same_role_by_permission(role, existing)
      if candidate:
        report("疑似同义: %s 与 %s,证据: %s" % (role.name, candidate, evidence))
      else:
        report("疑似新角色: %s,出现于 %s" % (role.name, role.sources))
  # agent 只输出报告,标准名的确立由 PM 决策
```

## 7. 禁止事项

1. ❌ 修改已确立的角色标准名(由人类决策)
2. ❌ 仅凭名字相似就归并两个角色
3. ❌ 用 `ROLE-XXX` 编号作为跨文档的角色标识
4. ❌ 把权限矩阵中的状态限定(如 `DC（已配置）`)当作独立角色
5. ❌ 把合并列(如「管理员 / Drawing 团队」)当作单一角色
6. ❌ 自动判定同义写法中"哪个对哪个错"
7. ❌ 删除既有条目
8. ❌ 因某模块无需求文档就断定其角色不存在(见 `global-rules.md` §11 第 9 条)

## 8. 与下游 agent 的协作

`ROLES-shared.md` 更新后,下游所有 agent **必须**:

- 权限矩阵、用户故事、文案中的角色名一律取自 §1 标准名
- 生成前比对 §2 禁用词表,命中则改写为标准名
- 想用的角色不在 §1 中 → 报告给 PM,**不自创**
