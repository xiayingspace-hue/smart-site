> **文档用途**：记录产品版本规划、各版本包含的 REQ 清单，以及每个 REQ 当前的文档版本状态。
> 版本号遵循语义化版本（SemVer）：`Major.Minor.Patch`。

---

## 版本号规范

| 位 | 含义 | 触发条件 |
|----|------|---------|
| Major | 主版本 | 重大架构变化、不兼容的 API 破坏性变更 |
| Minor | 次版本 | 新增功能模块（新 REQ 上线） |
| Patch | 补丁版本 | 已有 REQ 的 bug 修复、文案调整、AC 细化 |

### 关于 output_ver 列的移除

原表设有 `output_ver` 列，本次重建时移除，原因是该值当前无法可靠取得：

- 96 份下游文档中约半数没有任何溯源元数据
- 有元数据的部分格式不统一（`source_req: REQ-005-pc (v0.3.5)` 与 front matter `version:` 两种）
- 同一 REQ 的不同下游文档记录的版本互不一致，例如 REQ-003F 的 UI 记 `0.1.0`
  而 FE / BE / QA 记 `0.5.0`，无法归并为单一 output_ver

改用「下游文档」列记录**哪些类型已生成**（可由磁盘直接校验）。待下游文档的溯源块
格式统一后，可恢复 output_ver 列。

## 版本管理操作流程

### 新增 REQ 时
1. 需求文件必须写全 front matter：`version` / `updated_at` / `req_title` / `depends_on`
2. 在"REQ 文档版本状态总表"新增一行，下游文档列填 `—`，状态设为 `🔴 下游缺失`
3. 在"需求依赖关系总览"的树中挂上该 REQ
4. 在"版本详情"对应版本的"包含 REQ"中登记

### 需求变更时
1. 修改需求文件，更新 front matter 的 `version` 与 `updated_at`
2. 在需求文件 §18 变更历史中追加一行，填写「影响下游文档」列
3. 将本表中该 REQ 的 `req_ver` 与 `最后更新` 同步，状态改为 `🟠 下游过期`
4. 按 §18 标注的影响范围重新生成下游文档，完成后状态改为 `✅ 同步`，
   并在下游文档列补上新生成的类型

### 版本发布时
1. 确认该版本所有 REQ 状态均为 `✅ 同步`
2. 在"版本发布历史"表中填写实际发布日期，状态改为 `✅ 已发布`
3. 打 git tag：`git tag -a vX.X.X -m "发布摘要"`，快照由 tag 承载

> 历史版本追溯用 git，不在仓库内复制文档副本：
> 查看某版本 `git show vX.X.X:requirements/pc/REQ-XXX-pc.md`，
> 对比版本差异 `git diff vX.X.X..vY.Y.Y`。
> 复制副本会让全库检索命中过期文档、agent 读到旧版规则，
> 也与 `rules/global-rules.md` §6「引用而不复制」相悖。
